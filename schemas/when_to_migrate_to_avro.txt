## Avro vs JSON Schema: Assessment for VLC

### Current State
We are using **JSON Schema** with Schema Registry (`producer/schemas/air.json`). The `schemas/*.avsc` files are placeholders for a potential Avro migration for the future.

### Benefits of Avro Over JSON Schema

| Aspect 			| JSON Schema (current) 			| Avro 					|
|-------------------------------|-----------------------------------------------|---------------------------------------|
| **Message size** 		| ~2-3x larger (field names in every message) 	| Compact binary, ~40-60% smaller 	|
| **Serialization speed** 	| Slower 					| ~2-5x faster 				|
| **Schema evolution** 		| Supported but less strict 			| Stronger compatibility guarantees 	|
| **Tooling** 			| Good 						| Excellent (Kafka ecosystem native) 	|

**For ~11 stations, polling every 5 min: The throughput is low enough that JSON Schema works fine.
Avro benefits become significant at high throughput.

### Complexity of Migration: **Medium**

### What Would Need to Change

**1. Schema files** (`schemas/air.avsc`, `schemas/weather.avsc`):

```json
{
  "type": "record",
  "name": "AirQualityReading",
  "namespace": "vlc.air",
  "fields": [
    {"name": "fiwareid", "type": "string"},
    {"name": "ts", "type": {"type": "long", "logicalType": "timestamp-millis"}},
    {"name": "so2", "type": ["null", "double"], "default": null},
    {"name": "no2", "type": ["null", "double"], "default": null},
    {"name": "o3", "type": ["null", "double"], "default": null},
    {"name": "co", "type": ["null", "double"], "default": null},
    {"name": "pm10", "type": ["null", "double"], "default": null},
    {"name": "pm25", "type": ["null", "double"], "default": null},
    {"name": "air_quality_summary", "type": ["null", "string"], "default": null},
    {"name": "lat", "type": ["null", "double"], "default": null},
    {"name": "lon", "type": ["null", "double"], "default": null}
  ]
}
```
**2. Producer changes** (`air_producer.py`):
```python
# Replace JSONSerializer with AvroSerializer
from confluent_kafka.schema_registry.avro import AvroSerializer

# Load .avsc instead of .json
SCHEMA_PATH = Path(__file__).parent.parent / "schemas" / "air.avsc"

# Change serializer instantiation
avro_serializer = AvroSerializer(schema_registry_client, AIR_SCHEMA_STR)
```
**3. Connector configs** (`jdbc-sink.timescale.air.json`):
```json
"value.converter": "io.confluent.connect.avro.AvroConverter"
```
**4. Dependencies**: Add `fastavro` or use confluent-kafka's built-in Avro support (already included).

**5. Timestamp handling**: Avro uses `timestamp-millis` (epoch ms) vs ISO strings — requires conversion logic.

### Decision on 2025-12-14

**Don't migrate yet.** The current JSON Schema setup is working well and appropriate for the throughput.
We will go with Avro when:
- We need to reduce Kafka storage/bandwidth significantly
- We are processing thousands of messages per second
- We need stricter schema compatibility enforcement

The placeholder `.avsc` files are for jump-starting the avro dream.
